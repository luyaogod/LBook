## A. 已定

| # | 决定 | 依据 |
|---|---|---|
| A1 | **一本书 = 一个文件夹**；文件夹名只用于显示，身份靠 `meta.json.uid` | `PLAN.md` 第 4.1 节 |
| A2 | **单个大 OCR JSON + 字节偏移索引**，不拆页、不做自有格式 | 实测：见 `baseline.md`（自检 665/665、294/294 全等；按页 0.04–0.13ms） |
| A3 | **扫描器必须是流式分块**，内存里不出现整个文件 | 第一版读整个文件进 Buffer，内存数字当场失真（+46MB vs +4MB） |
| A4 | **索引缓存先不做** | 冷扫 15.6MB 只要 36ms，读回缓存 0.06ms——不值得 |
| A5 | **应用对书的内容只读**；没有 `dirty`、没有 Ctrl+S、没有未保存提示 | `PLAN.md` 第 3 节 |
| A6 | **IPC 形状尽量不变**：`library:*` / `book:*` 返回的渲染层数据结构保持现状，只换背后的实现 | 让 Phase 1 的改动集中在主进程，渲染层少动就少出事 |
| A7 | **`ocr.json` 逐字节原样**：迁移不重排、不 pretty-print、不改键顺序 | 用户用编辑器改过、被别的工具格式化过，都不该由我们改写 |
| A8 | **页号 = `layoutParsingResults` 的数组下标** | PaddleOCR 的元素里没有页号字段 |
| A9 | **PDF 走真实文件的区间读**，删掉 zip 区间读那条路 | 实测快 1.7–10.6×，且少一层 yauzl 句柄缓存 |

## B. 待拍板（5 条）

| # | 问题 | 建议 | 影响 |
|---|---|---|---|
| **B1** | **Markdown 视图的数据源**：由块实时拼（`markdownFromBlocks`）还是读文件里的 `markdown.text`？ | **由块拼**。实测两者 95.2% 逐字节相等、99.4% 仅差空白、真正差异只有 1 页 1 个字符；由块拼才能做到"改块 → 两个视图一致" | `01` 任务 T7；`src/shared/markdown.ts` |
| **B2** | **阅读进度放哪**：`%APPDATA%\LBook\progress.json` 还是书文件夹内？ | **`%APPDATA%`**。它是"这台机器读到哪"，不是书的内容；放书里会让只读挂载/网络盘/git 都不舒服 | `01` 任务 T6 |
| **B3** | **是否保留"导入向导"**（应用创建新书文件夹）？ | **保留一个最小的**（选 PDF + OCR JSON → 建文件夹 + 写 meta.json），但**不保留任何后续编辑**。纯扫描要求用户自己会摆目录结构，起手门槛太高 | `01` 任务 T9（可延到 Phase 2） |
| **B4** | **是否保留 `.lbook` 读取能力**（双格式并存）？ | **不保留**：一次性迁移 + 原包留底，代码里只留迁移器 | `01` 任务 T8；删 `lbook/reader.ts` |
| **B5** | **是否要 git 友好**（我们生成的 JSON 一律两空格缩进 + 键序固定）？ | **要**。代价为零（`meta.json` 本来就是我们写的），收益是"一个库目录可以 `git init`" | `01` 任务 T3（meta.json 的写出格式） |
| **B6** | **删一本书 = 删文件夹**（`library:delete` 现在就是真删）？ | **移到 `_trash/`**（可撤销），而不是 `rm -rf` 用户的文件夹。真要彻底删，让用户自己去资源管理器删 | `01` 任务 T11 |

> B1–B6 定了之后，`PLAN.md` 第 11 节要同步改成"已定"，免得两边不一致。
